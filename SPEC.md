# The `decisions` format — spec 1

A **MADR profile**. Decision records are [MADR](https://github.com/adr/madr) 4.0 markdown files
with one added front-matter block that carries the machine-readable layer MADR deliberately does
not provide. Our files are valid MADR; MADR files are not necessarily valid here.

**The format must degrade to grep.** A repo with no tooling, no Dart, and no station adopts the
pattern by copying `templates/` and writing files. Tooling makes the register mechanical; it is
never required to make it readable.

## The model

A register is **a citation graph with force**, not a document tree.

Every decision carries force the moment it is recorded. Decisions carry typed edges to each other
and to the surfaces they govern. Consolidated documents — what most orgs call `ADR-000N` — are
**rendered views** over the graph: generated, never authored, never a destination.

Codification is compaction, not authorization.

## Location and identity

```
docs/decisions/2026-08-30-madr-profile.md      # an entry
docs/decisions/views/0004-landing-policy.md    # a generated view
```

Entries are `YYYY-MM-DD-<slug>.md`. **The slug is the identity**, unique per register, and the
citation handle is `<repo>#<slug>` — e.g. `the_grid#no-file-watching`.

Entries carry no sequence number. Under binding-on-write, agents record concurrently from separate
worktrees of the same repo; two sessions allocating the next integer produce two files that merge
cleanly and silently share an id. Slugs need no allocator at any tier, are self-describing in a
grep hit, and collide only when someone re-decides a settled question — which is a signal worth
raising, not an accident.

Views keep zero-padded sequence numbers. They are generated by one tool in one pass, so allocation
is serialized by construction, and the numbering preserves the familiar `ADR-000N` surface.

### Reference ids, where a work tracker exists

Tier 0 has no id but the slug. Where a repo uses [beads](https://github.com/gastownhall/beads), a
decision SHOULD also be minted as a **`decision`-type bead**, and the bead id becomes the stable
short reference. This is reuse, not invention: `bd` is already a collision-free distributed
allocator with a store, a dependency graph, and cross-store links.

- The **file is the source of truth**; the bead is an index entry pointing at it. On divergence,
  the file wins.
- **Mint before you cite.** Write the bead, then write the file carrying its id. Never the reverse.
- A `decision` bead makes the decision-landed → re-validate-open-work trigger a dependency edge
  rather than a new subsystem.

Beads MUST NOT be assumed by the base pattern. A register with no tracker is fully conformant.

## Entry format

MADR 4.0 front matter, plus a `register:` block.

```yaml
---
status: accepted                    # MADR
date: 2026-08-30                    # MADR
decision-makers: [nico, agent]      # MADR (RACI)
consulted: []                       # MADR
informed: []                        # MADR
register:
  spec: 1
  slug: madr-profile
  surfaces:
    - "docs/decisions/**"
  obsoletes: []
  updates: []
  obsoleted-by: null
  updated-by: []
  bead: null
  legacy-id: null
---
```

Body: MADR sections. Base the template on MADR's **`bare-minimal`** variant, not the full one —
Context and Problem Statement, Decision Outcome, Consequences, with Considered Options only where
options were genuinely weighed. The full MADR template pulls toward options analysis, and an agent
handed it will manufacture a fake options table to fill the heading. **Omit a section rather than
invent content for it.**

### Status — the MADR vocabulary carries force unchanged

| force | `status` |
|---|---|
| binding | `accepted` |
| superseded | `superseded by <slug>` |
| vacated | `deprecated` |
| rejected | `rejected` |

**Entries are born `accepted`. This profile never uses `proposed`.** That is binding-on-write
stated in MADR's own vocabulary.

### Edges — authored versus cached

Two supersession relations, after the IETF's RFC headers:

- **`obsoletes`** — this entry replaces the named one entirely. Read this one instead.
- **`updates`** — this entry substantively amends the named one, **which remains in force.**
  Read both.

The existing memento registers have been distinguishing these all along in title prose —
"RETIRING pending A5" is *obsoletes*, "A23(7)'s throw is RE-HOMED" is *updates* — with no field to
put it in.

| field | kind | who writes it |
|---|---|---|
| `obsoletes`, `updates`, `surfaces`, `spec`, `slug`, `bead`, `legacy-id` | **authored** | the author, once |
| `status`, `obsoleted-by`, `updated-by` | **cached** | the tooling, from the graph |

**The body is immutable; the force block is a mechanically-maintained cache.** Deriving force
purely from the graph would be cleaner, but a grepper opening a 2026 entry would read
`status: accepted` with no way to know it was overruled — fatal for tier 0. So the back-edges are
denormalized, and `decisions lint` is what keeps them honest.

This also bounds migration cost permanently: a spec bump can touch the cached block, never the
prose.

Following the IETF here in one more respect — publishing a successor and changing the
predecessor's status are **separate deliberate acts**, not one automatic cascade.

## Vacating

Vacating is a first-class operation, not an edit. It **requires a successor**: a replacement
decision, or an explicit entry recording that no rule governs the surface any more. Silence is not
a valid outcome.

Vacating fires two consequences off the `surfaces` edges — open work whose design touches those
surfaces is flagged for re-validation, and the reversal work can be filed against the affected
repos.

## The docket

The human-agent ratification event. Triggered by signal, never by calendar: register size, a
detected contradiction, a decision cited N times, or a pending vacate request. It produces a
worksheet — one row per decision needing a force change — and the dispositions are themselves
entries with the human in `decision-makers`.

**OPEN:** the trigger thresholds.

## Versioning

**The spec is an integer.** `register.spec: 1`, declared **per entry**. Formats have no patch
releases; even additive change breaks a strict validator, so the only question a reader asks is
which version this is. Per-entry rather than per-register because the register is append-only —
2026 entries stay in the 2026 format forever, mixed-version registers are normal and permanent,
and a file must be self-describing to a grepper.

**Artifacts are semver**, tagged `<name>-v<version>` per the house convention. `cli/dart/decisions`
and `grid_assets/decisions_grid_assets` version independently and each declares the spec versions
it reads and writes.

**Registers are not versioned.** A register is a directory.

Compatibility: **readers support every spec version ≤ their own; writers emit only their own.** A
breaking spec bump ships its migration tool in the same release.

## Linting

[`madrlint`](https://github.com/adr/madrlint) validates MADR *shape*, one file at a time. It is
worth running and it is not sufficient: our layer is the graph. `decisions lint` checks required
`register` keys, edge integrity and reciprocity, force-cache consistency against the graph, slug
uniqueness, that `surfaces` globs resolve, and that cross-repo citations resolve across the roster.

## Tiers

| Tier | What you get | Needs |
|---|---|---|
| 0 — prose | the format, templates, a greppable register, the skills as plain markdown | nothing |
| 1 — CLI | `decisions index / lint / render / obsolete / update / vacate`, JSON out | an ecosystem impl |
| 2 — grid | overlay-installed skills, the committee lens, roster-wide cross-repo index, decision beads | a station |

Cross-repo union is a tier-2 property because it needs a live roster: a station enumerates its
mounted substations at runtime. Backstage's ADR plugin is the only comparable thing in the
ecosystem and it crawls a static catalog instead.

## What is ours, and what is borrowed

Borrowed, deliberately: MADR's vocabulary, sections, `docs/decisions/` path, RACI fields, and
status values (MIT/CC0). The IETF's `Obsoletes`/`Updates` distinction and its separate-acts rule.

Ours, because nothing in the ecosystem does it: **binding-on-write with a docket** (every ADR tool
assumes proposed → review → accepted), **cross-repo union over a live roster**, and **decisions
linked to the work graph**.
